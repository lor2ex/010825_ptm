# RAG: Примеры задач и реальные компании

## Что такое RAG и зачем он нужен

Retrieval-Augmented Generation (RAG) — это архитектура, которая добавляет к LLM динамическую память: перед генерацией ответа модель сначала **ищет** релевантные фрагменты в базе знаний, а затем отвечает, опираясь на них. Это решает главную проблему обычных LLM — их знания статичны, общедоступны и не содержат корпоративных или специализированных данных.

---

## Три новые задачи, где RAG особенно полезен

### 1. 🏦 Поиск по нормативной и юридической базе

**Проблема без RAG:**
Финансовые и юридические документы — тысячи страниц регуляций, приказов, инструкций. Обычная LLM не знает актуальной нормативки и уверенно «галлюцинирует» несуществующие статьи законов. Юрист или аналитик тратит десятки минут на ручной поиск.

**Что даёт RAG:**
Модель отвечает строго по загруженному корпусу документов, цитирует конкретный абзац и даёт ссылку на источник. Если документ обновился — достаточно переиндексировать базу, переобучать модель не нужно.

**Реальный пример:** Московская биржа внедрила RAG-поиск по нормативной базе и ускорила поиск с **18 минут до 15 секунд** (×72).

---

### 2. 🩺 Медицинский поиск по историям болезней

**Проблема без RAG:**
LLM обучена на общедоступных данных и не знает истории конкретного пациента, локальных протоколов клиники и свежих клинических исследований. Принимать решения на основе «общих знаний» опасно — медицина требует точности и ссылок на источник.

**Что даёт RAG:**
Агент ищет похожие случаи в закрытой базе пациентов, извлекает релевантные фрагменты и передаёт их LLM вместе с вопросом врача. Каждый факт в ответе привязан к конкретной медицинской записи — это делает ответ проверяемым. Медицинские стартапы уже используют FAISS + T5 именно для поиска аналогичных клинических случаев.

---

### 3. 🛠️ Корпоративная база знаний для разработчиков

**Проблема без RAG:**
В крупных командах документация разбросана по Confluence, Notion, Jira, README и устаревшим вики. Новый разработчик тратит часы, чтобы найти, как настроить локальное окружение или почему было принято то или иное архитектурное решение.

**Что даёт RAG:**
Все внутренние документы индексируются, и разработчик задаёт вопрос своими словами — получает точный ответ с цитатой из нужного документа. LinkedIn улучшил качество поиска по корпоративной базе на **28%** именно с помощью RAG.

## Почему RAG побеждает дообучение (Fine-tuning)

| Критерий | RAG | Fine-tuning |
|---|---|---|
| Обновление данных | Переиндексировать базу (минуты) | Переобучить модель (дни + деньги) |
| Проверяемость ответа | Есть ссылка на источник | Модель «знает» — источник непрозрачен |
| Стоимость | Низкая (векторный поиск дёшев) | Высокая (GPU, датасет, время) |
| Работа с закрытыми данными | ✅ Данные не покидают контур | ⚠️ Данные входят в обучение |
| Точность на узкой теме | Высокая | Высокая (но требует много примеров) |

## Вывод

RAG наиболее ценен там, где три условия выполняются одновременно:

1. **Данные закрытые** — корпоративные документы, медкарты, нормативная база
2. **Данные меняются** — новые законы, обновления продукта, свежие исследования
3. **Ответ должен быть проверяемым** — юридическая, медицинская, финансовая сфера

В этих условиях RAG даёт то, что обычная LLM дать не может: актуальность, точность и ссылку на источник.
